# MySafeSpace — Security Architecture: Development Phase 1

Status: **NOT APPROVED FOR REAL TESTIMONY / NOT PRODUCTION-SECURE**  
Date: 2026-11-14

## Scope of this phase

Implemented:

- A standalone, browser-side AES-256-GCM encrypt/decrypt **primitive** for synthetic data (not called by the application).
- Non-extractable transient AES-GCM keys generated using Web Crypto secure randomness.
- Fresh 96-bit IVs for each encryption operation and a 128-bit authentication tag.
- Versioned ciphertext envelopes, context-bound authenticated associated data, strict input validation and size limits.
- Tests for round trips, integrity failure, wrong keys, distinct IVs and non-exportability.
- Deployment header rules in `public/_headers` for **Cloudflare Pages static assets**; actual response headers must be inspected on the deployed service. Workers deployments may need headers enforced in worker responses instead.
- Tests run before the build in GitHub Actions.

This module is **not** wired into the editor, does not write any data to a server, and is not a complete zero-access vault. The 12-word screen is still UI-only.

## Phase 2 — 12-word recovery phrase encoding (isolated)

Implemented in `src/security/recovery.ts`, with tests in `recovery.test.ts`:

- Pinned `@scure/bip39` package, using its English 2,048-word list.
- Twelve-word mnemonic encoding of 128 bits generated by a cryptographically secure random-number generator.
- BIP39 checksum verification for a fully supplied phrase.
- Normalization of letter casing and pasted whitespace; no corrections or fuzzy guessing of missing words.
- Test-only decoding back to 16 bytes of source entropy for round-trip validation.
- No network requests, account creation, vault lookup, key derivation, server authentication, or storage.

**This does not unlock a real vault.** The package's previous audit does not replace independent review of the full MySafeSpace protocol. BIP39 checksum detects some typing errors; it is not an authentication mechanism, a password reset service, or proof that the survivor has safely retained their words.

**Outstanding before live phrase generation:** independently review the full key-wrapping and anonymous authentication protocol; decide on compatible recovery formats; verify client delivery integrity; create the actual recovery confirmation flow; and demonstrate that neither the phrase nor any key material reaches the server or logs.

## Phase 3 — vault-key wrapping experiment (isolated)

Code: `src/security/key-wrapping.ts` and `src/security/key-wrapping.test.ts`.

- Uses the existing 12-word BIP39 phrase to decode **128-bit randomly generated entropy** locally.
- Uses Web Crypto HKDF-SHA-256 with a fresh per-vault salt, a domain-separated context, and a random opaque vault ID to derive an in-memory AES-256-GCM **wrapping key**.
- Generates a *separate, random 256-bit data-encryption key*; encrypts that key with AES-GCM and a new 96-bit IV, authenticating the vault ID in associated data.
- Returns a versioned encrypted key envelope with only public metadata and the wrapped key. The unwrapped data key is imported as a **non-extractable CryptoKey** for use only in synthetic tests.
- Validates envelope structure and rejects changed metadata, ciphertext, an invalid phrase, and the wrong valid phrase.
- Neither recovery words nor source entropy are returned in the envelope; no network requests or storage are implemented.

**Experimental cryptographic protocol, not reviewed or launched.** HKDF is appropriate for this *uniformly generated, high-entropy* source; it is **not a password-hardening KDF** and does not make weak human-chosen phrases safe. The experimental function currently exposes a `CryptoKey` to its caller, which must remain within the trusted browser context. JavaScript memory clearing is best-effort only. This experiment does not implement real entry-key hierarchy, secure frontend delivery, server authentication, replay protection, data persistence, recovery confirmation or account deletion.

**Critical unresolved requirement:** A valid phrase must not itself become a reusable bearer token at the API. The real storage access protocol needs an independently assessed design that prevents the service from receiving phrase entropy or decryption material, and protects the encrypted vault against unauthorized reads, overwrites, deletion and enumeration. Do not derive a predictable public lookup key by hashing the recovery words. Any separate authentication credential must be generated and used without leaking vault secrets.

**Before changing the user interface:** Validate browser behaviour and CI, review the exact protocol and dependencies with an independent cryptographer/security professional, plan for secure software updates and server-side metadata protection, and design the complete backup/recovery lifecycle. Live encryption/recovery buttons remain intentionally disabled.

## Phase 4 — anonymous access proof prototype (isolated)

Code: `src/security/access-proof.ts` and `src/security/access-proof.test.ts`; a **non-deployed** Cloudflare D1 draft lives at `docs/PROTOTYPE_VAULT_SCHEMA.sql`.

The experiment uses P-256 ECDSA public-key challenge/response:

1. The test client generates an ephemeral, non-extractable signing private key and exports its **public** verification key.
2. The test server generates a fresh 256-bit nonce, vault ID, intended action and short expiry; it records the exact issued challenge.
3. The client signs domain-separated canonical bytes containing the nonce, vault ID, action and expiry.
4. A verifier checks the signature with the public key, rejects a different vault/action/expired challenge, and consumes the nonce once to reject replay.
5. Test coverage includes wrong keys, changed messages, expiry, wrong actions, repeated use and malformed input.

**Not yet resolved:** how to recover the signing private key with a 12-word phrase. A non-extractable in-memory private key vanishes after closing the browser and cannot be recovered by the current code. It needs a separately designed, securely wrapped exportable-then-imported private key or a reviewed deterministic design, and a proper registration protocol. Do **not** turn this prototype into live authentication without that.

**Critical distinction:** a signed proof is not, on its own, a server authorization system. Production requires atomic server-side challenge issuance/consumption across Worker instances; identity and action binding; register/recover flows; rate limiting and enumeration resistance; secure session handling; transactional authorization for every record operation; rigorous logging minimization; and external review. A JavaScript Map is test infrastructure only.

The draft D1 tables specify opaque IDs, public verification keys, encrypted key envelopes, append-only ciphertext entries and one-use challenge records. **No migrations, bindings or endpoints have been deployed.** Encrypted-data retention, backups, restores, timestamps, cryptographic chain integrity, legal preservation and user-initiated deletion require separate design.

## Phase 5 — recoverable signing credential experiment (isolated)

Code: `src/security/signing-recovery.ts`, `src/security/signing-recovery.test.ts` and the cross-module `src/security/vault-lifecycle.test.ts`.

- Generates a random P-256 ECDSA signing key pair and exports only the public verification key as JWK metadata.
- A briefly extractable private key is *wrapped* using Web Crypto `wrapKey("pkcs8", ...)`, with an AES-256-GCM key derived from the BIP39 entropy through HKDF-SHA-256.
- Uses an **independent domain tag and a fresh salt** for signing-key wrapping, separate from the data-key wrapping module.
- Binds the encrypted PKCS8 backup to the public verification key and vault identifier using authenticated associated data.
- The returned private signing key is non-extractable. Recovery uses `unwrapKey(..., false, ["sign"])`, also producing a non-extractable key.
- Recovery signs a random local test message and verifies it against the supplied public JWK, detecting mismatched key pairs.
- The cross-module test serialises only encrypted envelopes and synthetic ciphertext, then restores both the data-decryption and authentication credentials using the **same 12-word phrase**.
- Reconciles the vault locator to canonical URL-safe Base64 to match the access-proof prototype. **This locator is public metadata, not a recovery secret and not an authorization credential.**

**Important constraints:** A private key must be temporarily extractable when created for encrypted backup. A hostile frontend script or compromised device could potentially steal it at that point; reimporting it as non-extractable does not eliminate the threat. Recovery words and decrypted credentials are processed in the browser's memory and cannot be guaranteed erased. No browser memory, state, encrypted backup, authentication proof or API is persisted/sent by this module.

**Not a production vault:** This code is not connected to the website, authenticated registration, distributed challenge verification, server storage or recovery UI. A valid recovered key is not proof of server authorization until the verification key is authenticated against a securely registered vault, challenges are consumed atomically and every endpoint enforces authorization. Ciphertext rollback, missing entries, retention, recovery UX, abuse protections and independent review are all unresolved.

**Next development gate:** execute the full crypto test suite and TypeScript build in CI; review the key lifecycle with an independent cryptographer; design authenticated enrollment and recovery of the *vault locator* without leaking sensitive inputs. Do not activate storage or accept real testimony until those gates are complete.

## Phase 6 — isolated authenticated ciphertext store

Code: `src/security/synthetic-vault-store.ts` and `src/security/synthetic-vault-store.test.ts`. **In-memory synthetic test harness only**. Nothing is bound to Cloudflare Workers, deployed to D1, or accessible by real users.

Implemented in the harness:

- Register a vault only after a one-time signature proving control of the proposed public verification key.
- Match vault identifiers across the data-key backup and signing-key backup.
- Require a one-use, action-specific signed challenge for reading ciphertext, appending entries, exporting ciphertext or deleting the test vault.
- Restrict storage to versioned encrypted-entry envelopes, validate metadata and ciphertext encoding/size, and reject duplicate entry IDs or out-of-sequence revisions.
- Return encrypted backups and ciphertext rather than plaintext or recovery words. Tests verify that synthetic secrets are not present in serialized storage output.
- The simulated delete operation clears only an in-memory test Map; it is **not** production deletion.
- Regression tests include wrong signing keys, cross-vault access, replay, conflicting revisions and unsupported inputs.

**Important blockers before real storage:**

1. **Circular recovery:** The current harness requires a signed proof to fetch the encrypted signing-key backup, but the signing key needed to produce the proof is contained in that backup. A real returning user could not bootstrap recovery. A carefully designed retrieval mechanism must solve this without leaking or making enumerable private vault metadata. No public recovery endpoint has been enabled.
2. **Authorisation must bind the complete request:** The current proof signs a vault ID, action, challenge nonce and expiry—not the *append body*, revision, or deletion details. A live API must sign or otherwise authenticate the exact method/path/body digest and operation-specific revision to prevent alteration or substitution.
3. **Atomicity:** In-memory Maps do not provide distributed, transactional challenge consumption, vault creation, revision assignment or deletion. Cloudflare D1/Durable Objects implementation must enforce authorization and mutation atomically, including races, retries and idempotency.
4. **Server trust:** A server can still omit, reorder or roll back encrypted entries. Per-entry authenticated metadata, verifiable chains and client-verifiable integrity anchors require a reviewed scheme.
5. **Operations and compliance:** No rate limits, anti-enumeration measures, session lifecycle, key rotation, deletion retention, backups, incident response, privacy impact assessment, safeguarding or independent penetration testing yet.

**This is not a complete secure vault.** Avoid calling it production-ready, deploying the draft schema, creating live endpoints, or accepting real survivor testimony.

## Phase 7 — unauthenticated encrypted-key bootstrap (isolated)

Code: `src/security/recovery-bootstrap.ts`, `src/security/recovery-bootstrap.test.ts`, and extensions to `src/security/synthetic-vault-store.ts`. **Not deployed or connected to the website.**

- A deterministic, domain-separated HKDF-SHA-256 lookup identifier is derived **inside the browser** from the 128 bits of CSPRNG-generated BIP39 entropy. It differs from vault encryption and signing keys. It is 32 bytes, represented as 43 base64url characters.
- The test registration accepts a lookup ID and stores an index to the vault. An unauthenticated lookup returns **only the versioned encrypted backup envelopes, public verification key and opaque vault ID**, never entry ciphertext, plaintext, recovery words or signed permissions.
- The client locally unwraps the data key and signing private key. Subsequent ciphertext reads still require a one-time signed challenge using the recovered private key.
- Tests exercise returning in a simulated fresh browser, independent vault lookup, wrong words, duplicate identifiers and lookup removal on test deletion.

**Unresolved safety and privacy issues:** The lookup identifier is a stable pseudonymous account locator, **not anonymous metadata**. An attacker who knows it can request the key backup; an encrypted backup may permit offline guessing and account-existence checks. Security depends on truly random 128-bit recovery phrases, independently assessed cryptographic construction and robust client integrity. Avoid leaking the lookup ID via GET paths, query strings, referrers, analytics, logs or third-party scripts. A future lookup should use a carefully designed POST body under strict log suppression and strong rate limits; even then the operator would observe requests and linkability. Claims of absolute anonymity are inappropriate.

**Registration binding gap:** The current registration challenge signs the vault/action/nonce/expiry but **not** the lookup ID, encrypted envelopes or registration request digest. Malicious clients and request alteration could misbind a lookup ID to a different vault or backup. The prototype does not prove that the submitting client knows recovery words matching its lookup ID. This must be addressed in the reviewed authenticated-registration protocol before deployment.

**Storage gap:** In-memory Maps and public backup lookup are test-only. The real implementation must avoid timing/enumeration leaks, perform atomic request authorization and mutations, secure backups against rollback, provide durable data consistency, design safe deletion and disaster recovery, and undergo independent security and UK privacy review.

## Phase 8 — registration intent binding (isolated)

Code: `src/security/registration-intent.ts`, `src/security/registration-intent.test.ts`, plus updated `synthetic-vault-store.ts` and regression tests.

The initial signature proved possession of a signing key but did not cover the recovery lookup identifier or key backups. This version requires a **second P-256 signature** over domain-separated, fixed-order registration fields: vault ID, challenge nonce/action/expiry, lookup identifier, encrypted data-key envelope, encrypted signing-key envelope, and public-key coordinates. The prototype verifier requires that intent signature **as well as** the existing one-time challenge proof before registering a vault.

Tests cover legitimate enrollment and failure when an attacker substitutes the lookup identifier, either encrypted envelope, or the signing key; previously successful challenges cannot be replayed.

**Remaining security gap:** Even if the registration signature covers a supplied lookup ID, it does **not** prove the ID was derived from the exact recovery phrase that decrypts the encrypted key backups. A malicious or buggy client could create an unrecoverable vault. Production must design a suitable proof of consistency or safe local confirmation with recovery and registration validation, without disclosing the phrase or providing password-guessing oracles. The proof also does not atomically bind subsequent append bodies to signatures. Concurrent registration and storage are not safe with Maps. A formal protocol audit and transaction design remain required.

## Phase 9 — client-side recovery-consistency gate (isolated)

Code: `src/security/recovery-consistency.ts`, `src/security/recovery-consistency.test.ts`, `src/security/prepare-registration.ts`, and `src/security/prepare-registration.test.ts`.

The experimental browser-side registration preparation now **fails closed** unless the entered 12-word phrase:

1. Deterministically derives the exact supplied recovery lookup identifier.
2. Successfully unwraps the encrypted data key and produces a non-extractable decryption key.
3. Unwraps the signing key and verifies that it matches the public verification key supplied for registration.
4. Matches the vault identifier in both encrypted envelopes.
5. Passes a local signing/verification challenge before signing the registration proof and registration intent.

The helper returns only the signed registration payload and encrypted/public metadata. It does **not** return recovery words or unwrapped keys. All crypto operations are in memory, and no external API or database is contacted.

**Security boundary:** This is an honest-client check, not a cryptographic proof to the server that the recovery phrase matches the lookup ID. A malicious or modified client can skip it and register irrecoverable or deliberately inconsistent data. A real protocol still needs recovery-confirmation UX, server acceptance criteria, secure frontend distribution, transactionally consistent registration and independent cryptographic review. The current test-only data encryption also does not authenticate vault/revision metadata, so evidence integrity remains incomplete.

## Phase 10 — D1 atomic ciphertext append prototype (non-deployed)

Files: `docs/D1_TRANSACTIONAL_PROTOTYPE.sql`, `src/security/d1-transaction.ts`, `src/security/d1-transaction.test.ts`, and `scripts/test_d1_schema.py`.

- Draft SQLite/D1 schema has immutable registered verification keys and encrypted recovery backups, unique challenge nonces and consumed-nonce constraints, ciphertext-only rows and trigger-enforced sequential append revisions.
- The append prototype signs an exact canonical request (vault, challenge, entry ID, revision and encrypted envelope); the verifier loads the **registered public key from D1**, rather than trusting a caller-supplied key.
- A request digest is persisted when issuing a challenge. Later append executes `D1.batch([claim nonce, insert ciphertext])`. A missing/expired/mismatched challenge, replay, duplicate revision or trigger violation aborts the transaction. No plaintext or phrase goes into SQL.
- The challenge issuance step checks that exactly one row was inserted, failing closed for an unknown vault.
- Tests exercise request tampering, wrong verification keys, expired authorization, simulated batch failures, and SQL constraints. SQLite regression tests are also added to GitHub Actions.
- **No D1 database binding is configured, no schema is applied to any Cloudflare database, no API endpoint is exposed and no survivor data is handled.**

**Unresolved:** D1 concurrency and batch semantics must be tested against a dedicated disposable Cloudflare D1 test database, and errors/race conditions evaluated. The prototype has no secure atomic registration path or authenticated read/export/delete API. Secure challenge delivery requires an abuse-resistant endpoint, rate limits and metadata minimization. Signed append fields are still **not bound inside the entry AES-GCM AAD**, and operator-independent rollback/omission detection remains unsolved. The schema and adapter must receive independent technical review before any real-data deployment.

## Phase 11 — local concurrent-writer constraint regression

- Added `scripts/test_d1_concurrency.py` to run two concurrent SQLite connections against a disposable file-backed database and require exactly one commit at the same revision. The losing transaction must roll back nonce consumption.
- Added the concurrency check to `.github/workflows/ci.yml`, alongside the earlier schema, cryptographic test and TypeScript build jobs.
- A manual local check using a reconstructed copy of the draft schema confirmed one of two competing writers succeeded and only one challenge was consumed. This does **not** establish that GitHub CI has passed or that Cloudflare D1 uses identical locking and transaction semantics.
- The user's Cloudflare D1 binding exists in `wrangler.jsonc`, but **no remote D1 migration, INSERT or API request has been performed** by this phase.
- Next verification gate: inspect CI results, test a disposable isolated D1 database with artificial ciphertext only, review transaction failure behavior under concurrent Workers, and obtain independent protocol/security review before live enablement.

## Phase 14 — authenticated D1 ciphertext read/export prototype

Code: `src/security/d1-read-export.ts` and `src/security/d1-read-export.test.ts`.

- A read or export challenge is scoped to a registered vault, action, and requested starting revision, with a request-specific SHA-256 digest persisted in D1.
- The client signs a canonical, domain-separated request. The test-only server adapter loads the registered public JWK from D1 and validates the signature, rather than trusting a key supplied by the requester.
- A D1 batch claims the one-time challenge nonce and selects **ciphertext only**. A replayed, absent, altered or expired nonce fails before returning records.
- Full ciphertext exports are separately authorized, must begin at revision zero, and fail closed on missing or discontinuous revisions rather than silently returning a partial export.
- Automated synthetic tests cover wrong keys, altered actions/revisions, expired challenges, simulated replay errors, and incomplete exports.
- The live Worker remains **unconnected** to this module. No real Cloudflare D1 migration or requests have been performed.

**Limitations:** The vault metadata read (including latest revision and encrypted backup) occurs before the D1 batch, so a concurrently appended record can make an export fail closed. This does not establish a durable snapshot or anti-rollback guarantee. Ciphertext row metadata is not yet included in AES-GCM authenticated data; a malicious server could still suppress or substitute entries. This is deliberately limited to non-deployed synthetic tests; do not enable real evidence storage until independent security review, compliance assessment, and the remaining authorization protocols are complete.

## Phase 15 — authenticated record history and deletion-pending prototype

Files: `src/security/integrity-chain.ts`, `src/security/integrity-chain.test.ts`, `src/security/d1-deletion.ts`, `src/security/d1-deletion.test.ts` and updates to `docs/D1_TRANSACTIONAL_PROTOTYPE.sql` and the SQLite regression.

**Evidence integrity experiment:** a separate version-2 AES-256-GCM envelope includes vault ID, entry ID, revision and the previous envelope digest in authenticated additional data (AAD). SHA-256 hashes the resulting complete envelope and links each revision to the previous revision. Test helpers reject altered metadata/ciphertext, reordering, discontinuities, wrong keys and chain-head mismatches. This module is NOT yet connected to the existing version-1 D1 append/read adapters. An operator can still remove the entire chain or present an older valid chain unless the client retains and checks an independently trusted head digest. Timestamps are not independently attested.

**Deletion experiment:** a signed deletion challenge is scoped to a single vault and the precise `mark-deletion-pending` action. D1 batches challenge consumption and a conditional status change; a trigger rejects stale deletion claims once the vault is not active. Pending deletion blocks further appends. **No content is physically deleted, and the status transition is not proof of erasure.** Actual erasure of rows, encrypted key envelopes, provider backups and logs, retention/hold exceptions, recovery policy, and user-facing confirmation require explicit legal, safety and operational decisions before any deployment.

All of the above is synthetic/test-only, with no routes or live D1 migration. The complete CI suite still needs independent verification.

## Threat model (initial)

Protect against:

1. Public browsing or enumeration of another survivor's records.
2. Theft of database and blob storage contents.
3. A curious or malicious administrator with storage access.
4. Credential guessing and recovery-token replay.
5. Exposure of plaintext through analytics, logs, third-party scripts, caches and accident-prone client persistence.
6. Tampering with encrypted records or their original chronological history.
7. Malicious modification of deployed JavaScript, dependencies or release pipelines.
8. Exposure through shared or monitored devices, browser history, device downloads, and metadata.
9. Accidental data loss due to unavailable storage, lost recovery phrases or incomplete backups.
10. Legal retention demands, abuse reporting and safeguarding incidents.

Out of scope of a privacy *guarantee*: compromised client devices, keylogging, malicious browser extensions, unsafe downloads, coercion, or an attacker who replaces served client code. These risks need explicit survivor-facing explanations.

## Future cryptographic protocol — requires design review

Do **not** integrate the transient-key prototype into persistent vaults. The real protocol must decide and document:

- 12-word phrase encoding, entropy, checksum, robust secret parsing and documented compatibility.
- How a phrase relates to an opaque vault locator **without putting the secret in URL, referrer, browser history or server logs**.
- Authenticated anonymous vault access without exposing a reusable decryption credential to the server.
- Independent data-encryption keys per entry, and a reviewed key hierarchy and key-wrapping scheme.
- Migration, versioning, IV uniqueness, authenticated metadata, and rollback/replay protection.
- Append-only originals with verifiable hashes and accurate timestamp semantics.
- Key loss, recovery-word confirmation, deliberate session lock, and safe failure behaviour.
- Authenticated deletion, retention and disaster recovery without operator access to plaintext.
- Secure export for survivor-directed police sharing, without automatic reporting.

Do not build a homemade phrase-to-AES direct-key conversion. A fast cryptographic hash of a passphrase is **not** an acceptable replacement for a reviewed recovery architecture. Avoid adding a backend until this protocol, the authenticated request model and an independent review plan are documented.

## Current handling of writing

The existing React editor stores plaintext in memory **only during the current tab session**. It is **not encrypted or saved** and has no API. It is intentionally marked **DESIGN PROTOTYPE**. Do not enter real testimony, names, or identifying details. A refresh loses the draft; navigating within the SPA may retain it temporarily.

## Deployment security checklist

- Confirm whether the hosting target is Cloudflare Pages or a Worker serving static assets.
- Inspect actual response headers at the live URL; `_headers` applies to Pages static assets but is **not** a universal guarantee for Workers.
- Confirm HTTPS, HSTS, CSP, no-frame policy, referrer restrictions and no-store behaviour.
- Test direct routes (/write, /vault, /return) on refresh.
- Audit for third-party scripts/requests, logs, data sent to endpoints and embedded content.
- Pin dependencies and use a reviewed deployment pipeline with branch protection and MFA.
- Run automated tests in CI; independently test browser compatibility, security headers and integrity failures.
- Obtain external cryptography assessment, penetration testing, legal review and a DPIA before enabling storage of sensitive data.
